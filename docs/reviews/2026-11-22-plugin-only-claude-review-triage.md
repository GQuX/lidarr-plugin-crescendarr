# Independent plugin-only merge architecture review: source triage and execution gates

**Date:** 2026-11-22. **Reviewed material:** user-provided Claude read-only feasibility report against stock Lidarr v3.1.6.5079 (pinned upstream commit `da7b4dfb1a9e7e1d6625c2dbc3fff96971ab26bd`) and Crescendarr main at `da2f04a`. This document paraphrases/validates findings; it is not a claim that all proposed crash-safety properties are proven.

## Assessment

**Conditional go for further experimental tests; NO-GO for a write-enabled plugin.** The architecture is promising because it does not override Lidarr's import interfaces or require upstream patches, but the report's statement that it protects audio and lyrics against *every* stock-code crash point is **not executable evidence**. Partial native tests and real CDH-off completed-item discovery do not prove a correct replacement transaction.

### Confirmed stock-Lidarr mechanisms

1. [CDH gate](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/Download/DownloadProcessingService.cs#L47-L76): native Completed Download Handling OFF stops the stock automatic `ICompletedDownloadService.Import` call for import-pending jobs, and `DownloadsProcessedEvent` is still published. [PR #20](https://github.com/GQuX/lidarr-plugin-crescendarr/pull/20) actually observed a synthetic completed item through a configured client on disposable stock Lidarr with CDH OFF, then verified the setting persisted after ordinary plugin removal/restart.
2. [Stock `ImportApprovedTracks.Import` lines 120-132](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/MediaFiles/TrackImport/ImportApprovedTracks.cs#L120-L132): passing `replaceExisting=false` skips **only** the album-wide pre-delete; it **still invokes** `IReleaseService.SetMonitored` for the first approved release. Passing pinned overrides into the decision maker is not yet a tested guarantee against unexpected release identity changes.
3. [Native upgrader](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/MediaFiles/UpgradeMediaFileService.cs#L42-L84): per-target existing file and TrackFile row removal happens before move/copy. A verified independent backup is a possible mitigation for audio bytes, but not a proof of database or lyric safety, and a hardlink on the same filesystem is not an independent storage backup.
4. [ExtraFileService lines 67-95, 103-129](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/Extras/Files/ExtraFileService.cs#L67-L129): `Delete(id)` calls only the extra-file repository, not the physical file recycler. The `TrackFileDeletedEvent` handler recycles **registered** extras returned for that TrackFileId; an already-unlinked lyric is not in that association. This makes unlink-first worth testing.
5. **Important fix to Claude's recovery sequence:** native `Upsert` calls `InsertMany` for ID **zero** and `UpdateMany` for ID **greater than zero**. Both repository methods are invoked even for an empty list; only matching rows are affected. A deleted `LyricFile` cannot simply be `Upsert`ed using its former nonzero ID. Restore must insert a fresh row with `Id=0`, preserve correct metadata/relative path and link to a verified new TrackFile ID. [PR #22](https://github.com/GQuX/lidarr-plugin-crescendarr/pull/22) characterizes this with mocked native service plus real **disposable SQLite** and a tiny synthetic `.lrc`.
6. [EventAggregator.PublishEvent lines 105-121](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/Messaging/Events/EventAggregator.cs#L105-L121) runs `IHandle<T>` callbacks synchronously; exceptions from each handler are caught/logged and not rethrown. [ProcessMonitoredDownloadsCommand](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/Download/ProcessMonitoredDownloadsCommand.cs) has `RequiresDiskAccess=true`, and `DownloadsProcessedEvent` is published inside its execution. The existing [command queue](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/Messaging/Commands/CommandQueue.cs#L159-L172) avoids starting another queued RequiresDiskAccess command while one is started. This is **command scheduling coordination, not a comprehensive global filesystem lock**, and does not guarantee exclusion of external NAS writers or API mutations.
7. [DiskScanService.ExcludedSubFoldersRegex](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/MediaFiles/DiskScanService.cs#L37-L38) excludes dot-prefixed subfolders from normal scan filtering. A hidden `.crescendarr` operation folder is a plausible staging place, but must be checked against **all** scanners, cleanup jobs and user configurations; the regex alone is not a storage-isolation guarantee.
8. [DownloadEventHub.Handle(DownloadCompletedEvent)](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/Download/DownloadEventHub.cs#L48-L68) calls the configured download client's `MarkItemAsImported`, and if removal is enabled, it may invoke `RemoveItem(item, deleteData:true)` at lines 87-94. The plugin must settle **only after** media, lyrics, edition and recovery status are verified. [DownloadHistoryService](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/Download/History/DownloadHistoryService.cs#L190-L208) records a download-import event; this is not proof that each track is correct.

### Corrections / remaining uncertainty

- **CDH-off synthetic Blackhole metadata:** Claude suggested the PR #20 Blackhole item had no grabbed history *or category*. The pinned `UsenetBlackhole.GetItems` sets `Category = "Lidarr"`; therefore the specific no-category rejection would **not** apply. However the synthetic title is not a real identified artist/album, and the experiment did not prove a valid `RemoteAlbum` or ImportPending mapping. A separate disposable grabbed-item/known-artist scenario is still needed. [CompletedDownloadService.Check](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/NzbDrone.Core/Download/CompletedDownloadService.cs#L57-L104) performs additional path and artist checks.
- **Lyric rescue isn't automatic:** A crash between unlink and relink leaves `.lrc` bytes on disk but may leave no database association. Subsequent `ExistingLyricImporter` can re-register only under its actual name/path/track identification rules; an audio rename or a competing scan may invalidate the assumption. It requires an operation journal and real scenario tests.
- **Stock file publication isn't transactional:** even if a verified original copy exists, crashes between old TrackFile DB delete, new file transfer, bulk AddMany and SetFileIds can leave a discrepant database. A suggested `re-run Import` during recovery is **not** safe by default: it must not operate on a stale path/edition or duplicate links. Hold on ambiguous states.
- **Scan races still matter:** a queued RescanFolders command may be serialized with the completed-download command, but other paths, process crashes and a restart can expose a missing original path before recovery. [Native MissingFromDisk test](../compatibility/native-history-rescan-characterization.md) shows registered lyric deletion under that condition. `.crescendarr` scan exclusion does not prevent cleanup of the missing **original** path.
- **Zero-improvement settlement is a product decision:** `DownloadIgnoredEvent` records DownloadIgnored history and leaves the client data outside the normal completed-removal path. It may be acceptable but is not necessarily a truthful or desirable substitute for a verified no-improvement album that is already fully satisfied. Never equate ignored with imported without explicit semantics and cleanup/retention policy.
- **Manual import is outside the plugin's CDH-off safety boundary.** ManualImportCommand uses RequiresDiskAccess but can still run when the plugin is absent. No broad guarantee that stock manual imports are made safe by Crescendarr.
- **SMB guarantees are bounded:** checksum/readback, hardlinks and renames are storage-specific and do not make Lidarr DB plus NAS atomic. A crash test on disposable local bytes is needed before a *separate dedicated synthetic SMB share*, never production media.

### Next gates before implementation

1. **Native SQLite + synthetic `.lrc`**: execute delete/insert/association with real migrated test DB, ensure bytes retained, and show nonzero-old-ID `Upsert` cannot restore a missing record. [PR #22](https://github.com/GQuX/lidarr-plugin-crescendarr/pull/22) (pending CI at drafting).
2. **Full native synthetic import**: source-pinned `ImportApprovedTracks.Import(...false)` against real temporary *audio-like* files and a disposable SQLite DB; assert 11 approved improvements, 12th untouched; release pinned; .lrc association relinked. Can use synthetic test media or isolated audio fixtures; never user library.
3. Inject a real failure in file six then verify old bytes, native TrackFile/Track IDs and lyric records are recoverable after a fresh process/test startup. Test scan before restoration.
4. Separately test `DownloadsProcessedEvent` coordination, event failure behavior, and real grabbed/download mapping with CDH OFF. Validate `DownloadCompletedEvent` and `DownloadIgnoredEvent` side effects with a synthetic client that is **not configured to remove real files**.
5. Only after tests 1-4 pass consider a *read-only by default* plugin executor prototype. Do not ship or install write-enabled Crescendarr yet.

**Current answer:** yes, the single-plugin stock-Lidarr direction remains plausible. No, safe recovery after every crash, correct edition protection and full `.lrc` retention have not been demonstrated. The independent report is useful as a **candidate architecture**, not approval to enable writes.
